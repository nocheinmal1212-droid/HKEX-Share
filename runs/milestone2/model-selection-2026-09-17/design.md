Question: does a Flash configuration provide supported direct-addend interpretation sufficiently consistently to justify a provisional development default? Does a non-Flash configuration offer measured debugging/fallback value? No business error budget is set. These are exploratory thresholds, not owner-approved production acceptance criteria. Gemini 3.8 Flash is a separate comparison reference, never ground truth.

All eight exact owner IDs and the exact Gemini oracle appear in freshly saved official models and endpoint metadata. No substitution. configurations.json binds primary/secondary endpoint tags, advertised provider, price, parameters, canonical slug and native reasoning defaults. Pin one route, disable routing fallbacks, require supported parameters. Primary routes avoid historical failed Fireworks pools. Secondary routes are only a predeclared availability arm. Report every arm separately. Provider name/returned model is an API assertion, not weight attestation; canonical dates are metadata, not measured capability. ## Stages and advancement

1. Availability/capability probe: one S03 call for every model, in owner order with Gemini last. This doubles as the first common screen observation. An HTTP/transport failure permits one separate S03 availability call on its frozen secondary endpoint, not a same-route retry. Two unavailable probes end that model's experiment. A usable but wrong, abstaining or invalid completed output does not remove a candidate from the screen. If only truncation occurs, retain the primary route and complete the common screen. Authentication/account failure stops all dispatch.
2. Common screen: S03, S04, S08, S11, S09, S10 once per available configuration. Remaining cases run in that order, rotating model order by 2 positions each case and reversing alternate rounds. All six expected outcomes are reviewed below before fresh outputs. Do not drop difficult cases because of a wrong answer. A new service error ends that configuration's remaining screen calls; omitted cases remain explicit unavailable coverage. No further service probing beyond the two availability routes.
3. Budget arm: for each model with truncation and otherwise available route, repeat only its earliest truncated screen case once at 8,192 tokens, same prompt/route. Count separately; never replace initial score. If usable/full-pass, freeze 8,192 for that model's confirmation; otherwise retain the common configuration and report budget unresolved. This arm is offered to every qualifying candidate and oracle.
4. Confirmation: choose one Flash and one non-Flash with no unsupported selection in screen, at least 5/6 source-correct completed decisions, and a correct S03 selection. Rank eligible configurations by full screen passes, then lower measured total reported cost (missing costs lose ties), then median all-attempt latency, then owner order. No weighted score. A sole truncation resolved in the budget arm may satisfy the 5/6 rule but remains visible. If no member of a group qualifies, leave that role unvalidated; do not lower the threshold. Gemini continues if available independently of its score. Freeze chosen configurations before confirmation. Run H01, H02 and S11 twice each: 18 calls at most, with reversed model/case order on repeat two. H01/H02 are never used for tuning or finalist selection. Report S11 repetition separately from new pair; two correlated repeats are not independent cases. A provisional sufficient *fixture* configuration must pass all six screen cases and all six confirmation attempts with relevant support, no unsupported selection, and no unavailable result. Anything weaker remains conditional or unvalidated.
5. Explanation follow-ups run only after initial scores and confirmation settings are frozen; they never enter scored prompts or change scores. Up to two screen/budget diagnostics per model: first completed wrong answer/refusal (if any), and first correct abstention (if any), ordered by actual attempt. A wrong abstention is in the first class. Up to one additional confirmation diagnostic per model: earliest completed wrong/refusal, otherwise first correct abstention. This is a maximum 27 calls. Enumerate all qualifying omitted decisions and unavailable diagnostics. Use original messages and original response in a separate conversation; no expected answer, wrong-answer label or alternative answer. Request concise source-cited explanation, missing evidence and smallest clarification, no replacement answer or private reasoning. Check IDs/excerpts; explanations are fallible hypotheses.

Ceilings across all inference/probes/tuning/diagnostics: **117 calls**, **1,000,000 requested completion tokens**, **4,000,000 input-token planning allowance**, **USD 35 reserved maximum at frozen route rates**, **120 minutes of dispatch wall time**. Exact bodies are at most 32,000 UTF-8 bytes; input allowance is conservative planning, because provider tokenization is not locally attested. ## Scoring, persistence and selection

Report action/exact unordered contributors separately from reason, required-support coverage, extra-citation relevance and valid contract. Abstaining on a supported case is unnecessary abstention; selecting unsupported or incompatible contributors is unsupported selection. Refusal, invalid output, truncation, timeout and HTTP/service errors have distinct columns. All-attempt denominators include failures; usable-answer conditional correctness is additional. Candidate–Gemini agreement is exact action/contributors, with reason agreement separate, only on matched available case/repeat responses. Resolve disagreements against frozen source review, never majority vote. A valid wrong answer is not a detectable runtime fallback trigger.

No automatic cascade will be recommended from this design: it does not measure a trigger-driven cascade. Service fallback and interpretation debugging can be future experiments, but correct missing-evidence abstention never calls for a larger model to guess. No deployment designation, production wiring or scoring gates change.

Reuse unchanged v2 source/request/response/result/completion records. New configurable transport recomputes exact wire request from the dispatched payload. All batches are exclusive new directories, keys outside worker. OS sandbox plus exact-read audit guard must deny root .env, raw injector metadata, original fixture files and evaluator keys through both pathlib and os.open before calls. Runtime receives selected sources and requests only. Diagnostics use the same v2 persistence envelope; its unchanged semantic validator will mark the explanation-shaped output invalid for select_direct_addends. Score diagnostic schema separately, never as a semantic attempt. Resolve any commit_unknown through read-only replay without resending.
